# CoinFlow MVP PRD

이 문서는 CoinFlow 거래소 MVP의 제품 범위와 기능 요구사항을 고정하기 위한 PRD이다.

MVP의 목표는 단일 인스턴스 환경에서 지정가 주문 생성, 취소, 매칭, 체결, 정산, 조회까지 이어지는 거래소 핵심 파이프라인을 오류 없이 검증하는 것이다.

## 1. 배경

CoinFlow는 암호화폐 거래소의 핵심 백엔드 도메인을 직접 구현하는 프로젝트다.

MVP에서는 실시간 시세, 입출금, 복잡한 권한 모델, 분산 인프라보다 주문과 자산 정합성을 우선한다. 사용자는 간단한 회원가입/로그인 후 지정가 매수/매도 주문을 생성하고, 시스템은 시장별 순차 처리로 가격-시간 우선 매칭을 수행한다. 체결이 발생하면 주문, 체결, 지갑, 원장, 이벤트 로그가 일관되게 기록되어야 한다.

## 2. MVP 목표

- 지정가 주문 생성과 취소를 지원한다.
- 간단한 회원가입과 로그인을 지원한다.
- JWT access token으로 API 요청 사용자를 식별한다.
- 동일 시장의 주문 처리 순서를 보장한다.
- 가격 우선, 시간 우선 매칭을 수행한다.
- 부분 체결과 완전 체결을 처리한다.
- 매수 주문 시 quote asset을 잠그고, 매도 주문 시 base asset을 잠근다.
- 체결 시 매수자/매도자 지갑을 정산한다.
- 지갑 변동은 append-only 원장으로 기록한다.
- 주문, 호가, 체결, 사용자 관점 fill, 지갑, 원장 상태를 조회할 수 있다.
- 주요 도메인 이벤트를 이벤트 로그에 기록한다.
- 향후 Kafka, outbox, replay, recovery로 확장 가능한 경계를 남긴다.

## 3. MVP 성공 기준

- 정상적인 주문 생성, 주문 취소, 매칭, 체결, 정산, 조회 시나리오가 오류 없이 동작한다.
- 주문 생성부터 결과 조회까지의 파이프라인이 끊기지 않는다.
- 지갑의 `available_balance`, `locked_balance`가 음수가 되지 않는다.
- 주문 수량 불변식이 유지된다.
- 체결 금액과 원장 기록이 일치한다.
- 로그인 사용자는 자신의 주문, 지갑, 체결 fill, 원장만 조회/변경할 수 있다.
- 서버 시작 시 DB의 미체결 주문으로 메모리 오더북을 초기화할 수 있다.
- MVP 제외 범위가 구현에 섞이지 않는다.

## 4. 사용자와 전제

### 사용자

- 거래 사용자: 주문 생성, 취소, 조회를 수행한다.
- 개발자/운영자: DB, 원장, 이벤트 로그를 통해 정합성을 검증한다.

### 전제

- MVP에서는 회원가입, 로그인, JWT access token 발급/검증을 구현한다.
- 비밀번호는 평문 저장하지 않고 hash로 저장한다.
- 인증이 필요한 API는 JWT에서 현재 사용자 ID를 꺼내 사용한다.
- 주문 생성, 주문 취소, 주문 조회, 지갑 조회, 원장 조회, fill 조회는 로그인 사용자 기준으로 처리한다.
- 계정별 주문, 지갑, 체결 fill, 원장은 현재 사용자 ID 기준으로 반드시 분리한다.
- 입출금은 구현하지 않고, 테스트용 seed wallet balance를 사용한다.
- MVP에서는 지정가 주문만 지원한다.
- MVP에서는 `GTC` 주문만 지원한다.
- 수수료와 dust 처리는 제외한다.

## 6. 핵심 도메인 정책

### 인증 정책

| 항목 | MVP 정책 |
|---|---|
| 회원가입 | email, password, nickname 기반 |
| 로그인 | email, password 기반 |
| 비밀번호 저장 | password hash 저장 |
| 인증 방식 | JWT access token |
| refresh token | 제외 |
| 권한 모델 | 제외 |
| API 사용자 식별 | JWT subject의 user id |

인증이 필요한 API는 request body나 query string의 `userId`를 신뢰하지 않는다. 서버는 JWT에서 현재 사용자 ID를 추출하고, 해당 사용자 기준으로 주문, 지갑, 원장, fill을 처리한다.

### 주문 정책

| 항목 | MVP 정책 |
|---|---|
| 주문 유형 | 지정가 주문 |
| 주문 방향 | `BUY`, `SELL` |
| Time in force | `GTC` |
| 시장가 주문 | 제외 |
| 주문 취소 | `OPEN`, `PARTIALLY_FILLED`만 가능 |
| 체결 가격 | maker 주문 가격 |
| 자기 체결 | MVP에서는 거절 |
| client order id | 사용자별 중복 방지에 사용 |

### 주문 상태

| 상태 | 의미 |
|---|---|
| `OPEN` | 미체결 주문 |
| `PARTIALLY_FILLED` | 일부 체결 후 잔량 존재 |
| `FILLED` | 전량 체결 |
| `CANCELED` | 사용자가 잔량 취소 |

### 자산 잠금 정책

| 주문 | 잠금 자산 | 잠금 수량 |
|---|---|---|
| `BUY` | quote asset | `price * quantity` |
| `SELL` | base asset | `quantity` |

### 정산 정책

| 대상 | 처리 |
|---|---|
| 매수자 quote wallet | 체결 수량에 해당하는 예약 금액을 locked에서 차감하고, maker 가격 기준 차액은 available로 환불 |
| 매수자 base wallet | 체결 수량만큼 available 증가 |
| 매도자 base wallet | 체결 수량만큼 locked 감소 |
| 매도자 quote wallet | 체결 금액만큼 available 증가 |

### 매칭 정책

- BUY 오더북은 높은 가격이 우선이다.
- SELL 오더북은 낮은 가격이 우선이다.
- 같은 가격에서는 낮은 `sequence`가 우선이다.
- 체결 가격은 항상 maker 주문 가격이다.
- 동일 시장의 주문 생성/취소 명령은 시장별 queue에서 순차 처리한다.

### Trade와 Fill 정책

| 용어 | 의미 | 저장 방식 |
|---|---|---|
| Trade | 시장에서 발생한 체결 1건 | `trades` 테이블에 저장 |
| Fill | 특정 사용자 주문 관점의 체결 내역 | 별도 테이블 없이 `trades`에서 파생 조회 |

하나의 trade는 매수자 fill 1건과 매도자 fill 1건으로 해석할 수 있다.

사용자별 fill 조회에서는 `maker_order_id`, `taker_order_id`를 기준으로 유동성 역할을 계산한다.

```text
요청 주문이 maker_order_id와 같으면 liquidity = M
요청 주문이 taker_order_id와 같으면 liquidity = T
```

## 8. API 범위

MVP API의 정확한 request/response schema는 별도 API 명세서에서 관리한다. PRD 기준으로 필요한 API는 아래와 같다.

| Method | Path | 설명 |
|---|---|---|
| `POST` | `/api/v1/auth/signup` | 회원가입 |
| `POST` | `/api/v1/auth/login` | 로그인 및 JWT access token 발급 |
| `GET` | `/api/v1/users/me` | 현재 사용자 조회 |
| `GET` | `/api/v1/markets` | 시장 목록 조회 |
| `POST` | `/api/v1/orders` | 주문 생성 |
| `POST` | `/api/v1/orders/{orderId}/cancel` | 주문 취소 |
| `GET` | `/api/v1/orders/{orderId}` | 주문 단건 조회 |
| `GET` | `/api/v1/orders` | 주문 목록 조회 |
| `GET` | `/api/v1/markets/{market}/orderbook` | 호가 조회 |
| `GET` | `/api/v1/markets/{market}/trades` | 최근 체결 조회 |
| `GET` | `/api/v1/fills` | 사용자 관점 체결 조회 |
| `GET` | `/api/v1/wallets` | 지갑 조회 |
| `GET` | `/api/v1/wallets/ledgers` | 원장 조회 |

## 9. 정합성 요구사항

### 지갑 불변식

```text
available_balance >= 0
locked_balance >= 0
```

### 주문 수량 불변식

```text
original_quantity = executed_quantity + remaining_quantity
remaining_quantity >= 0
executed_quantity >= 0
```

### 체결 금액 불변식

```text
trade.quote_amount = trade.price * trade.quantity
```

단, 실제 저장값은 market의 scale/rounding 정책을 적용한 확정 금액이다.

### 오더북 불변식

오더북에는 아래 상태의 주문만 존재할 수 있다.

```text
OPEN
PARTIALLY_FILLED
```

아래 상태의 주문은 오더북에 존재하면 안 된다.

```text
FILLED
CANCELED
```

## 10. 비기능 요구사항

- MVP는 단일 인스턴스에서 동작한다.
- 동일 시장 명령은 순차 처리되어야 한다.
- DB는 source of truth이다.
- 메모리 오더북은 파생 조회 모델이다.
- 모든 잔액 변경은 원장에 기록되어야 한다.
- 주문, 체결, 정산, 원장, 이벤트 로그는 같은 트랜잭션 안에서 기록되어야 한다.
- 메모리 오더북은 트랜잭션 commit 이후에만 변경되어야 한다.
- API 응답의 금액/수량은 문자열로 표현한다.
